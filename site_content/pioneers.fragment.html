How do proposals become releases?

Issues are proposals. Maintainers agree on scope before a linked PR, review the change and its evidence, and connect it to the release. Seth owns the project direction and approves the website's rendered release proof. The human building the app owns its intent and acceptance.

The issue-first policy is our direction; its shared public policy and required GitHub checks are being prepared. Read the current process and remaining work →

What's ready, and what's on the frontier?
  • Supported: the stable web path covers routing, ECR pages and forms, Grant records, migrations, jobs, WebSockets, and local assets. See its platform and feature matrix. Generated authentication/API resources, Gemma, and native apps have separate preview boundaries.
  • Available: the public docs MCP searches and reads Amber guides. Minecart's tools are distributed in the installed Shards Alpha build.
  • In progress: app MCP and agent setup have open CLI PRs. Local performance-budget tooling exists; its public release and CI gates remain open.
  • Proposed automation: one release bundle keeps the website, roadmap, library docs, agent catalogs, and updates on the same verified identity. The coordinated beta.5 web release is the working foundation.
  • Exploration: WebMCP could expose page actions to browser agents. It is a Chrome origin-trial capability, with its own browser-support gate.

Mobile is the next expedition. Our first call is for people building web apps.
