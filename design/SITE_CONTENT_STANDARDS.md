# Amberframework.org content and guide standard

This file is the working agreement for humans and agents who write, revise, or
review Amberframework.org. Update it when the team accepts a better recurring
pattern. A guide review must name the version of this file it used by linking to
the reviewed commit or recording the local file checksum.

## 1. What every page should do

A reader should understand these things in this order:

1. what they are about to make or learn;
2. what the finished result looks like;
3. what is available in the released toolchain today;
4. which file or command they should touch next;
5. how to verify that step;
6. where to continue when it works.

Technical completeness does not excuse a confusing reading order. Architecture
belongs next to the decision it helps the reader make.

## 2. Amber’s voice

Amber writes like a capable friend who is excited to build with the reader.

- Use first person naturally: “I’ll show you,” “we’ll build,” and “our app.”
- Speak directly to the reader as “you.”
- Lead with the visible result, then explain the mechanism.
- Prefer short paragraphs with one idea each.
- Explain a technical term the first time it affects the reader’s decision.
- State limitations plainly and briefly. Give the usable path immediately.
- Let excitement come from what the reader can make, not from marketing claims.
- Use contractions when they make the sentence sound natural.

Amber does not narrate internal deliberation, dump an implementation audit into
the tutorial, or make the reader reconstruct the intended workflow from a list
of caveats.

Avoid:

- “The point of this section is…” when the result can be stated directly;
- repeated “current implementation” and “contract boundary” paragraphs;
- long preambles before the first visible result or runnable command;
- treating web, iOS, Android, and macOS as separate products when the subject is
  an Amber Everywhere monolith;
- claiming that generated files, compilation, or a simulator screenshot proves
  physical-device behavior;
- invented APIs or future commands presented without a preview label.

## 3. Tutorial flow

Use this sequence unless the subject gives you a concrete reason to change it:

1. **Invitation:** Amber tells the reader what they are building.
2. **Finished view:** show a screenshot or mock and describe the useful result.
3. **Status note:** one compact note distinguishes released and preview pieces.
4. **Smallest working start:** give the first command and its working directory.
5. **Build in reader order:** introduce files when the reader needs them.
6. **Connect behavior:** show how UI intent reaches controllers and use cases.
7. **Style and resources:** provide complete copyable assets and name every path.
8. **Verify:** give observable checks for the relevant target.
9. **Continue:** link to the next focused guide.
10. **Remaining work:** put roadmap gaps at the end unless they block an earlier
    step.

Each tutorial milestone should end in an observable result before the reader
moves to the next page. When a page depends on another page, name that
prerequisite before the first dependent snippet. A multi-page guide must still
have one obvious assembly order.

When a guide is also a generator acceptance application:

- lead with the exact generation command instead of making the reader manually
  reconstruct files the generator already owns;
- include the immutable template version and digest beside a remote manifest;
- distinguish a locally served template, a published template, and a proposed
  future channel;
- show the generated shared parent before platform host details;
- make manual snippets match the generated bytes, or label them as an
  adaptation rather than the generated result;
- when a remote bundle replaces a built-in scaffold, remove every obsolete
  route, entrypoint, view, and example model through a generator-owned cleanup
  contract; do not leave an unreachable second interface for the reader to
  discover;
- regenerate a clean project from the documented command during review and
  inspect its template lock before approving the guide.

Reference pages may be denser, but their introduction should still tell the
reader why the reference matters to the application they are building.

## 4. Amber Everywhere examples

The canonical monolith story uses one shared application and view tree.

- Shared screens live under `src/views/`.
- Shared use cases live under `src/app/`.
- Web and native controllers adapt different event systems to those use cases.
- ECR may provide an Amber document or layout bridge; it must not duplicate the
  shared product interface.
- When a tutorial converts a generated scaffold to a shared screen, name every
  generated view, action, and route that the reader must remove or replace.
  Never leave a second, reachable ECR interface behind.
- Platform hosts live under one parent application and may optimize rendering,
  lifecycle, navigation, services, packaging, and resources for their platform.
- Diagrams and file trees must make the shared parent visually obvious.
- Desktop web may use available width differently. Mobile web, iOS, and Android
  should preserve the same hierarchy, labels, color roles, and touch targets.

## 5. Code examples

Every code block must answer “where does this go?” locally or through a clear
page-level file map.

- Format Crystal examples with `crystal tool format --check`.
- Compile complete Crystal examples against the documented dependency revision.
- Use actual public APIs from that revision.
- Keep dependent snippets consistent across the guide section.
- Include require and entrypoint wiring; a file that is never loaded is not a
  runnable example.
- Treat routes as owned wiring. When a registry replaces manual or generated
  routes, tell the reader which declarations to remove so both cannot match.
- Keep synchronous, callback, and async contracts consistent from the use case
  through every controller and adapter that calls it.
- Prefer stable semantic or `test_id` selectors over DOM position.
- Show complete copyable CSS when the page promises a finished style.
- State the working directory for commands that depend on it.
- Mark proposed commands and APIs as preview at the place they appear.
- Markdown-rendered pages cannot call ECR asset helpers. Link to the generated
  fingerprinted URL from the asset manifest and explain how to refresh it when
  the source asset changes.
- Do not use placeholder resources without explaining how every target resolves
  them.

## 6. Visual identity

### Primary Amber identity

The primary Amber mark is the existing character asset:

`app/assets/characters/amber-chibi-hero-mark-v2.webp`

Use the exact checked-in asset. Do not ask an image model to redraw, reinterpret,
or replace it. The faceted crystal at `app/assets/brand/amber-crystal.svg` is a
supporting motif. Product-specific marks, such as Pet Tracker’s paw, belong
inside that product and must not replace Amber’s site identity.

### Generated mockups

- Treat generated UI images as design references until the rendered app is
  captured from a real target.
- Put **Design reference — not a runtime screenshot** in every generated UI
  figure caption. Do not rely on a later disclaimer.
- If runnable code intentionally omits or changes something visible in the
  reference, list the difference beside that figure.
- Preserve approved layout, palette, and hierarchy when deriving assets.
- Extract reusable subjects into separate files with transparent backgrounds.
- Store the final prompt set and output paths under `design/`.
- Use alt text that describes the interface relationship, not the generation
  process.
- Never let model-generated brand marks replace checked-in brand assets.

## 7. Truth and release status

Use these words consistently:

- **Supported:** part of the documented release gate.
- **Preview:** available for evaluation, with named missing gates.
- **Proposed:** documentation or design contract that is not implemented.
- **Verified:** attach the source revision, target, environment, and observable
  result.

Keep these proof gates separate: source generation, compilation, package
inspection, simulator/emulator runtime, physical-device runtime, and cold
relaunch persistence.

## 8. Adversarial review protocol

The reviewer assumes the page may be technically accurate and still fail the
reader. Review the rendered page from top to bottom and answer:

### Reader flow

- Can a new reader state what they are building after the opening paragraph?
- Does the finished result appear before the implementation detail?
- Is every step actionable when encountered?
- Are prerequisites and working directories explicit?
- Does the page postpone non-blocking roadmap detail until the end?

### Voice

- Does Amber sound like one person speaking to the reader?
- Are first person and “you” used naturally rather than mechanically?
- Does any paragraph read like hidden reasoning, an audit log, or generated
  filler?
- Can any paragraph lose half its words without losing required meaning?

### Technical and runnable quality

- Do code blocks name their destination?
- Do linked snippets agree on types, filenames, identifiers, and commands?
- Do examples format, compile, or otherwise validate at the appropriate level?
- Are visual assets and CSS sufficient to reproduce what the page promises?
- Are web and native event flows described without pretending they are the same
  runtime mechanism?

### Brand and platform integrity

- Is Amber’s checked-in primary mark preserved exactly?
- Are product marks clearly subordinate?
- Do mobile web, iOS, and Android preserve the same product hierarchy?
- Are platform optimizations described where they occur without splitting the
  monolith into separate applications?

### Truthfulness

- Is every supported, preview, proposed, and verified claim labeled correctly?
- Does each proof claim name what was actually observed?
- Could a reader mistake a mockup for a runtime screenshot?

Classify findings as:

- **Blocker:** could make the reader build the wrong thing, use an unavailable
  feature as released, lose the shared-view architecture, or misuse the brand.
- **Major:** breaks the tutorial flow, leaves a promised result unreproducible,
  or creates material ambiguity.
- **Minor:** worthwhile clarity, consistency, or polish improvement.

The review report must include evidence, the violated standard section, and a
specific proposed correction. After fixes, record each finding as resolved,
accepted, or deferred with a reason.

## 9. Updating this standard

When a review discovers a reusable lesson, update this file in the same change
as the guide. Keep page-specific preferences in the page or its design brief;
promote only patterns that should guide future Amber content.
